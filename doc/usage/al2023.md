## Building through Session Manager

To provision the builder over an AWS Systems Manager Session Manager tunnel, add
the following overrides to your custom Packer variable file:

```hcl
ssh_interface               = "session_manager"
source_ami_filter_name      = "al2023-ami-2023.*-kernel-6.18-*"
associate_public_ip_address = "false"
```

The non-minimal source AMI includes SSM Agent, which must be available before
Packer can connect. If overriding `source_ami_id`, select an SSM-ready image too.
Pass an approved `iam_instance_profile` with Systems Manager permissions when
building. The caller also needs permission to pass that role and start sessions,
and the local runner needs the Session Manager plugin installed.

Alternatively, set `temporary_iam_instance_profile_policy_document` in your custom
variable file to an IAM policy object with `Version` and `Statement` fields.
Each statement accepts `Effect`, an `Action` list, and a `Resource` string.
For SSM, use the permissions documented in
[AmazonSSMManagedInstanceCore](https://docs.aws.amazon.com/aws-managed-policy/latest/reference/AmazonSSMManagedInstanceCore.html).
Leave `iam_instance_profile` empty when using this option. Packer creates the role
and instance profile for the builder and removes them during cleanup. The caller
needs IAM permissions to create, configure, pass, and delete these resources;
organization policies and any permissions-boundary requirements still apply.

The builder subnet needs connectivity to Systems Manager and the package and
container repositories used by the build. A public IP and inbound SSH access are
not required for the Session Manager tunnel.

Packer still uses SSH authentication inside the tunnel and, by default, creates a
temporary EC2 key pair. Switching to Session Manager does not resolve an
organization policy denying `ec2:CreateKeyPair`.

## Building natively with SSM Run Command (no SSH)

For standard AL2023 nodes, `hack/build-ssm.sh` provides a standalone alternative to
Packer. It uses **SSM Run Command**, not SSH tunneled through Session Manager.
It never creates or imports an EC2 key pair, opens an SSH connection, or modifies
security-group ingress. Organization policies still apply to all AWS operations.

### Prerequisites

- AWS CLI, `jq`, `tar`, and Bash on the local runner, with AWS credentials.
  Neither Packer nor the Session Manager CLI plugin is required.
- An existing **private S3 bucket in the build account and region** for the source
  archive, version information, and SSM command logs. Treat this bucket as build
  infrastructure: block public access and set an appropriate retention policy.
- A subnet with outbound access to SSM, Amazon Linux repositories, the EKS binary
  bucket, and the container registries used by this repository. SSM VPC endpoints
  alone do not provide access to all build dependencies.
- An existing security group allowing the required outbound traffic. No inbound
  SSH rule is needed. The builder is launched without a public IP, so provide NAT
  or other approved private connectivity to repositories.

### Run a build

From the repository root, replace the placeholders below. Use the Kubernetes
minor version of your cluster and an AMI name you have not used before:

```bash
export AWS_PROFILE=image-builder

REGION=ca-central-1 \
K8S=1.37 \
ARCH=x86_64 \
SUBNET_ID=subnet-REPLACE_ME \
SECURITY_GROUP_ID=sg-REPLACE_ME \
ARTIFACT_BUCKET=YOUR_PRIVATE_BUILD_BUCKET \
AMI_NAME=org-eks-al2023-1.37-emudhra-001 \
bash hack/build-ssm.sh
```

This script **does not consume Packer variable files**. Run
`bash hack/build-ssm.sh --help` for its inputs. It reuses this checkout's default
and Kubernetes-minor-specific scalar variables, but intentionally disables EFA,
accelerators, and FIPS. Those variants are not supported by this workflow.
Architecture defaults to `x86_64`; `arm64` selects an ARM builder by default.

The script discovers published binaries using `hack/latest-binaries.sh`; it fails
if matching binaries are unavailable. To pin them, set both
`KUBERNETES_VERSION` and `KUBERNETES_BUILD_DATE` to published values.
It discovers a standard, non-minimal AL2023 source image with the kernel selected
by this checkout. Optionally pin `SOURCE_AMI_ID` to an SSM-ready AL2023 image with
the matching architecture and kernel family.

### Instance profile and caller permissions

By default, the script creates a temporary role and instance profile with
`AmazonSSMManagedInstanceCore`, plus S3 read/write permissions scoped to this
build's artifact prefix and bucket-location lookup. It removes them during
cleanup. Alternatively, set `INSTANCE_PROFILE` to an approved existing profile
with those permissions. Existing profiles are not modified or deleted.

The caller needs EC2 image discovery, launch, tagging, describe, image capture,
and termination permissions; `iam:PassRole`; S3 bucket access and artifact
read/write/delete permissions; and these SSM permissions:

- `ssm:DescribeInstanceInformation`
- `ssm:SendCommand` for `AWS-RunShellScript` and the builder instance
- `ssm:ListCommandInvocations`
- `ssm:GetCommandInvocation`
- `ssm:CancelCommand`

Temporary profiles additionally require:

- `iam:CreateRole`, `iam:DeleteRole`
- `iam:AttachRolePolicy`, `iam:DetachRolePolicy`
- `iam:PutRolePolicy`, `iam:DeleteRolePolicy`
- `iam:CreateInstanceProfile`, `iam:DeleteInstanceProfile`
- `iam:AddRoleToInstanceProfile`, `iam:RemoveRoleFromInstanceProfile`

This does not bypass SCPs or permissions-boundary requirements. If your
organization requires boundaries on new roles, use an approved existing profile.
The root EBS volume is always encrypted; set `KMS_KEY_ID` to use an approved
customer-managed key and ensure the relevant principals have its required KMS
permissions. Source archives and version-info uploads explicitly use SSE-S3;
bucket policies must permit that. If logs use a bucket-default customer-managed
KMS key, the instance role also needs appropriate KMS permissions.

### Lifecycle, validation, and outputs

The script launches one disposable builder, transfers only the required source
directories through S3, and runs this checkout's AL2023 installation scripts as
root via `AWS-RunShellScript`. It includes the CA-distrust step and repository
validation. It does not enroll the builder into an EKS cluster.
Provisioner ordering lives in `hack/ssm-build-instance.sh`; adding a provisioner
to the Packer template does not automatically add it to this workflow. Future
host-sensor installation should run before cleanup and validation, following the
vendor's golden-image procedure without baking enrollment secrets or identities.

Cleanup and validation execute while SSM can still report their status. DNS
configuration is temporarily restored after validation so command results can be
uploaded. A delayed systemd task then stops SSM Agent, removes that configuration,
SSM identity/state/logs, and build payloads, and powers off. The caller waits for
the stopped instance before capturing the AMI and for the AMI to become available
before reporting success.

The local outputs are `<AMI_NAME>-manifest.json` and
`<AMI_NAME>-version-info.json`. The manifest records the AMI ID, source AMI,
binary version/build date, region, and S3 log location.

On normal completion or failure, the script attempts to terminate its builder,
remove any temporary role/profile, and delete its uploaded source archive.
SSM logs and version information remain in the bucket. Cleanup failures are
reported explicitly and make the command fail. Versioned buckets can retain old
source-archive versions; configure lifecycle rules accordingly. A hard kill or
runner loss can leave resources behind: use the printed `eks-ami-ssm-*` run name
and builder ID to identify them. If image creation has already started, the AMI and snapshots
are retained even if waiting for availability fails.

This is a build workflow, not an end-to-end EKS certification test. Before using
the AMI in production, launch a test node group and validate first-boot identity,
cluster join, networking, workload behavior, and the host trust-store mitigation.
Container images and application-specific CA stores require separate assessment.

### Local orchestration tests

```bash
bash -n hack/build-ssm.sh hack/ssm-build-instance.sh hack/test-build-ssm.sh
bash hack/test-build-ssm.sh
```

These tests mock AWS and archive creation. They cover successful builds, reuse of
an existing profile, ARM and minor-version defaults, IAM/launch failures,
provisioning/finalization failures, AMI wait failure, cleanup failure, and missing input, without reading build payloads
or creating AWS resources.
They do not validate real AWS permissions, agent behavior, or AMI bootability.

## Accelerated images

One can build images that contain Neuron or Nvidia drivers and runtime configuration. To build Neuron image execute:

```
make k8s=1.29 os_distro=al2023 enable_accelerator=neuron enable_efa=true
```

To build an NVIDIA image:
```
make k8s=1.29 os_distro=al2023 enable_accelerator=nvidia enable_efa=true
```
The `lts` and `pb` driver trees default to major versions 580 and 595; set `nvidia_driver_lts_version` and `nvidia_driver_pb_version` to override. To see which driver versions are available, one can check the NVIDIA AL2023 [repository](https://developer.download.nvidia.com/compute/cuda/repos/amzn2023/).

## Pause Container Image

Since [PR #2000](https://github.com/awslabs/amazon-eks-ami/pull/2000), the pause
container image is no longer pulled in at runtime on AL2023. `nodeadm` uses a
static pause container reference to populate the
[`sandbox_image`](https://github.com/containerd/containerd/blob/963c2160485631c3d4c1068aa28cea34c884a347/docs/cri/config.md?plain=1#L314-L315)
field of the containerd config.toml, which is baked into the AMI during the
build based on the packer template variable `pause_container_image`.

The default for `pause_container_image` points to an EKS-owned ECR image, but
you can also use another pause image entirely such as `registry.k8s.io/pause`.

If you need coordinates for a different ECR image in another region, see
https://docs.aws.amazon.com/eks/latest/userguide/add-ons-images.html for a list
of region-specific registries that hold identical repositories.

Additionally, if you would like to use a FIPS endpoint, this will require just a
minor change to the registry URI:
```diff
-<ACCOUNT_ID>.dkr.ecr.<REGION>.<DOMAIN>"
+<ACCOUNT_ID>.dkr.ecr-fips.<REGION>.<DOMAIN>"
```
